# TPC-H SF1 correctness test (22 queries)

Runs the 22 TPC-H queries at scale factor 1 through RapidsSE's own SQL compiler, run-time
optimiser and execution engine, compares every result with an independent reference and writes
a per-query, per-stage matrix. A query counts as PASS only when it executed in RapidsSE and its
rows equal the reference.

    python3 tests/tpch_sf1_correctness/scripts/run_all.py            # one round
    python3 tests/tpch_sf1_correctness/scripts/run_all.py --rounds 3 # stability (three rounds)

Requirements: the built engine (`bin/rapidsse`), Java for the JDBC client in `shell/`, Python 3.
`TPCH_SF1_DATA` (or `--data-dir`) names the directory of the `.tbl` files; when a table is
missing, the data set is generated there with the DBGEN in `dbgen/`. The exit status is 0 only
at 22/22 in every round.

## Layout

    queries/q01.sql .. q22.sql   the query text that is sent to RapidsSE and to the reference
    queries/order_by.json        the ORDER BY of each query, for the comparison
    schema.sql                   tables, indexes, partitioning and the load statements
    reference/dataset.json       pinned row counts and SHA-256 of the eight data files
    reference/expected_results/  reference rows per query, and source.json: who produced them
    scripts/prepare_sf1.py       data set: generate if missing, check rows and checksums
    scripts/run_reference.py     reference results (DuckDB, or the official answer set)
    scripts/run_rapidsse.py      the 22 queries on RapidsSE, with plans, logs and stage results
    scripts/compare_results.py   comparison and final status
    scripts/run_all.py           all of the above and the report
    fixes.json                   which change made which query pass
    reports/LATEST.md            the matrix of the newest run that was committed

## Queries and dialect

The files in `queries/` are the query definitions of the TPC-H specification with the
validation substitution parameters (the ones the official answer set was produced with).
Nothing is simplified. The differences from the specification text are:

| Query | Difference | Reason |
|---|---|---|
| Q2, Q3, Q10, Q18, Q21 | `LIMIT n` at the end | The specification states "return the first n rows" outside the SQL text; `LIMIT` is how both RapidsSE and DuckDB express it. |
| Q15 | `WITH revenue0 AS (...)` instead of `CREATE VIEW` / `DROP VIEW` | The common-table-expression form is the variant the specification allows (Appendix B); it keeps the query a single statement. |

The reference runs exactly the same files. The only rewrite on the reference side is that
DuckDB does not accept the precision in `interval '90' day (3)` (Q1), which is removed there.

## Data

Scale factor 1, generated by the DBGEN of this repository (version in `dbgen/release.h`).
DBGEN has fixed seeds and takes no seed argument, so the data set is reproducible;
`reference/dataset.json` pins the row count and SHA-256 of each file. The test stops before
running anything when a table is missing, a row count differs from the specification
(region 5, nation 25, supplier 10,000, customer 150,000, part 200,000, partsupp 800,000,
orders 1,500,000, lineitem 6,001,215) or a checksum differs. After the load, the row counts
inside RapidsSE are checked as well.

## Reference

The reference is DuckDB, running the same query files over the same `.tbl` files. The
workflow `tpch-reference` produces it on a GitHub runner (data generated there with the same
DBGEN and checked against the pinned checksums) and commits the rows to
`reference/expected_results/`; `source.json` there names the DuckDB version. `run_reference.py`
regenerates them when the Python package `duckdb` is installed and otherwise uses the committed
files. The answer set that ships with DBGEN (`dbgen/answers`) is only a cross-check: it agrees
with DuckDB on 21 queries and differs on Q17 (348406.02 in the file, 348406.05 from DuckDB).
Results are never taken from RapidsSE.

## How results are compared

Fixed before the runs, the same for every query:

* The number of rows and the number of columns must be equal.
* Text, dates, integers and NULL must be equal exactly (trailing blanks of fixed-width text
  are ignored; NULL equals only NULL).
* Decimal values: the RapidsSE value is rounded half-up to the number of decimals the reference
  shows and may then differ by at most the tolerance in `source.json` (0.01, the rule of the
  TPC-H specification for the two-decimal answer set). There is no relative tolerance.
* Duplicate rows count: the results are compared as multisets.
* A query without ORDER BY passes when the multisets are equal.
* A query with ORDER BY must in addition return its rows in that order; rows whose sort keys
  are all equal may come in any order.

## Stages and failure classes

| Column | Evidence |
|---|---|
| Parser, Binder, Logical plan | `EXPLAIN <query>` in the SQL compiler; the plan is saved in `plans/qNN.explain.txt` |
| Optimizer, Physical plan | the optimised pipeline of the run-time optimiser (`/optimiser_trace`), saved in `plans/qNN.pipeline.txt` |
| Runtime | the execution returned rows without an error |
| Result | comparison with the reference |

Final status: `PASS`, `PARSE_ERROR`, `PLAN_ERROR`, `OPTIMIZER_ERROR`, `RUNTIME_ERROR`,
`WRONG_RESULT`, `TIMEOUT`, `CRASH`, `BLOCKED`, `NOT_RUN`. With more than one round, a query
whose status differs between rounds is `UNSTABLE` and does not count as passed.

Times are wall-clock times of the JDBC client for one execution, including the start of the
client (reported in every matrix as "client overhead"). They are for spotting regressions, not
a benchmark.

## Known limit: 16 significant digits

A decimal value in RapidsSE has a 56-bit mantissa, about 16 significant digits. A result that
needs more is rounded (half to even) to the digits that fit. `sum_charge` of Q1 needs 18 digits
to be exact at six decimals; RapidsSE returns it with five decimals and, because a running SUM
rounds on every row once it has outgrown the mantissa, with a random error of about 0.001 at
SF1. That is inside the 0.01 tolerance, but it is not an exact sum. An exact one needs a wider
accumulator for SUM, which is not implemented.

## Optimiser on/off equivalence

The run-time optimiser cannot be switched off as a whole: flattening the sub-queries and laying
out the stages is what makes a pipeline executable. The transformations that only make a plan
cheaper can be switched off per job, with the tags `/optimiser_off_<name>` and
`/optimiser_off_all` (`src/store/XF.cpp`): scan_to_indexscan, cut_sort, early_projection,
reduce_gbyagg_key, static_calc, max_to_top, aggreg_to_sort_ordagg, sortdesc_limit_to_top,
sort_limit_all_levels, early_filter, late_projection, duplicate_filter, local_gbyagg (no
node and origin merges for a GROUP BY on a column the stream is partitioned on); also join_rows
(join ordering by estimated rows, index joins on the index with the fewest rows per key),
join_dp (join ordering over connected orders only, keeping on one node the cheapest way to
join each set of tables), corr_semijoin (SQL compiler: key sets copied into correlated
sub-queries), eq_closure (SQL compiler: a = b and b = c add a = c to the filter), const_fold
(SQL compiler: DATE literal +/- INTERVAL literal computed once), scan_project (a projection
behind the filter of a scan stays in the stage of the scan), sll_parse (SQL parsed with
SLL prediction first, full LL only when that fails), hash_gbyagg (a GROUP BY keeps
its groups in a hash table, not in the payload tree), scan_prune (a table scan steps
over the columns its filters and project never read instead of inflating them) and
scan_gbyagg (a GROUP BY behind the project of a scan runs in the stage of the scan),
join_project (a projection behind an inner index join stays in the stage of the join) and
join_gbyagg (a GROUP BY behind that projection runs in the stage of the join) and
join_prune (an index or cross join skips the columns of the joined table that no operator
of its stage reads) and le_shortcut (an index join finds the upper end of its range from
the lower end instead of a second descent of the tree) and having_groups (a HAVING that compares each group with an aggregate
of the same groups, as in Q11 and Q15, is done in two passes over the groups in memory
instead of a second pass over the tables) and col_cache (a table scan reads its
fixed-width columns from the column cache of each CRW buffer instead of decoding
every row; see doc/design/columnar-scan.md), col_cache_join (an index join reads the
cells of the joined row from the column cache of its buffer instead of decoding it;
same document), hash_join (an inner index join on one
integer key stores the arriving rows by key and, at the end of its input, walks the
joined index once or looks the stored rows up in it; see doc/design/hash-join.md) and
hash_join_bloom (the walk skips index entries whose key has no stored row with a Bloom
filter).

    python3 tests/tpch_sf1_correctness/scripts/run_optimiser_equivalence.py

runs each of the 22 queries normally and with every switch (660 executions) and compares the
rows with the reference by the rules above. It writes `reports/OPTIMISER_EQUIVALENCE.md`.
It needs more memory than the correctness test (plans without early projection carry every
column); on a machine with 8 GB the node is killed for memory part of the way. CI has 16 GB.

## Where the time goes

    python3 tests/tpch_sf1_correctness/scripts/phase_times.py --clear-cache --repeat 2

runs every query with the job tag `/phaseTimes` and writes `reports/PHASE_TIMES.md`: per
query the time of the client, the SQL compiler, the run-time optimiser, the C compile of the
generated code and the execution, for the first run (compiled code not cached) and the repeated
one. `reports/PERFORMANCE_ANALYSIS.md` is the analysis.

## Continuous integration

`.github/workflows/tpch-correctness.yml` builds the engine with `-O2` and runs, on every pull
request and push to `main` that touches the source or this test, once a day, and on request:

* the correctness test against DuckDB on the same machine (one round; `rounds: 3` on request),
* the optimiser on/off equivalence test (including one run of every query with
  `/optimiser_validate`),
* the phase breakdown (`phase_times.py`),
* once a day and on request, the correctness test with 1, 4 and 8 partitions.

The job fails unless everything passes. The matrix is the job summary; plans, logs and rows are
the artifact. The matrix has a table with the time per query of RapidsSE and of DuckDB on that
machine. `.github/workflows/tpch-reference.yml` keeps the committed DuckDB reference current.

## Configuration that is run

`TPCH_SE_PARTITIONS` and `TPCH_SE_THREADS` set the partitions and threads of the node (default
2 and 2; CI uses 4 threads). Verified with 1, 2 and 4 partitions.

One node; in CI four partitions and four threads on the four CPUs of the runner (TPCH_SE_PARTITIONS, TPCH_SE_THREADS; the defaults of the scripts are two and two); `orders` partitioned on `O_CUSTKEY`, `region` and
`nation` replicated (see `schema.sql`). Several nodes and the RoCEPool backend are not covered by
this test yet.
